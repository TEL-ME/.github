## 프로젝트 개요

가상 통신사의 FAQ 1,150건을 근거로 사용자 질문에 답하고, 가까운 매장까지 안내합니다.

```
"유심 재발급 얼마예요?"
      ↓
  FAQ 검색 → 근거 있음 → AI가 근거로 답변 → Answer Guard가 근거 밖 수치, 채널 차단 → 출처 표시
      ↓
  FAQ 검색 → 근거 없음 → "확인이 어렵습니다" (AI를 아예 호출하지 않음)
```

<details>
<summary><b>기능별 상세 보기</b></summary>

### 1. FAQ 데이터 구축과 품질 관리

- 정책 기준 문서(`docs/POLICY.md`) 45개 항목을 먼저 확정하고, FAQ 답변은 그 수치만 인용
- 카테고리 10종 × 질문유형 5종 × 페르소나 3종 조합으로 표현 다양성 확보 → **1,150건 생성, 적재 완료**
- 임베딩 유사도 0.95 이상 중복 자동 탐지, 답변 수치와 정책 문서 값 자동 대조
- 생성 슬롯 식별자(`slot_id`)를 DB에 저장해 **같은 파일을 다시 적재해도 중복이 생기지 않음**

### 2. 벡터 검색 (RAG Retrieval)

- `bge-m3` 임베딩(1024차원) → pgvector 코사인 거리 top-3 검색, 컬럼별 HNSW 인덱스
- **이중 벡터**: 같은 FAQ를 `Q_A`(질문+답변)와 `QUESTION_ONLY`로 각각 임베딩해 **서로 다른 임계값(0.72 / 0.88)**으로 조회한 뒤 합침
  - 점수 척도가 달라 한 줄로 섞어 정렬하지 않고, 중복 제거 후 `QUESTION_ONLY` 우선으로 top-3 컷
  - 임베딩 호출은 1회 그대로, DB 조회만 2회 (지연 ×1.09)
- 검색 품질을 Recall@k / MRR, 무관 질문 거부율, AUC로 측정하고 개선 전후를 비교
- 실패를 유형별로 분류하는 도구를 만들어, 개선안이 **어떤 실패를 고치고 어떤 실패는 못 고치는지** 구분

### 3. AI 상담 파이프라인

- 질문 의도 분류(`FAQ` / `STORE` / `BOTH` / `UNKNOWN`)와 복합 질문 분해
- 검색 결과로 Context를 구성하고 EXAONE 3.5로 근거 기반 답변 생성
- 상담에 필요한 조건이 빠졌으면 되묻고(`CLARIFICATION`), 후속 답변과 조건 정정을 반영
  - 조건을 **거부한 경우(declined)와 아직 답하지 않은 경우(pending)를 구분**해 같은 질문을 반복하지 않음
- 답변의 근거 성격을 `GROUNDED` / `NO_EVIDENCE` / `OUT_OF_SCOPE` 세 값으로 남겨 UI가 다르게 표시
- 멀티턴 맥락 유지: 대화 요약 스냅샷과 커서를 저장해 긴 대화에서도 컨텍스트 길이를 관리
- 세션 제목을 첫 질문으로 자동 생성(최대 30자)

### 4. 답변 가드 (환각 차단)

- 생성된 답변을 **문장 단위로 검사해 근거에 없는 내용을 차단**
  - 금액(억, 만, 원 단위 정규화), 기간, 수량(영업일, 개월, %, GB 등), 시각(09:00 = 9:00), 비교 주장
  - 근거에 없는 채널 안내(앱, 홈페이지, 고객센터, 매장 등), 근거에 없는 결제 / 부가 정책(부가세, 위약금, 할부 등)
  - 사용자가 질문에 적은 값을 사실처럼 단정하는 문장
- "확인이 어렵습니다" 뒤에 붙는 설명은 근거 밖이라 잘라냄
- 선택 기능으로 **근거 적합성 2차 판정**(검색이 통과시킨 근거가 질문에 실제로 답하는지 LLM에 한 번 더 확인)을 설정으로 켤 수 있음

### 5. 실시간 응답

- SSE 이벤트 5종: `start`(생성 시작) / `token`(답변) / `status`(`RETRYING`) / `complete` / `error`
- 메시지 상태 `GENERATING` / `COMPLETED` / `FAILED` / `TIMEOUT` / `CANCELLED`, 실행 상태 `RUNNING` / `COMPLETED` / `FAILED` / `CANCELLED`
- **DB 저장을 끝낸 뒤 전달한다**: 연결이 끊겨도 답변은 남고, 새로고침 후 이력 조회의 `runningExecutionId`로 다시 구독
- 가드를 통과한 최종 답변만 내보내므로 FAQ 답변은 **완성본 1회 전송**이고, 타이핑 연출은 프론트가 담당
- 실행당 구독 1개. 다른 탭이 같은 실행을 구독하면 먼저 연결된 쪽에 `CONNECTED_ELSEWHERE`를 보내고 끊음
- LLM 호출 실패는 재시도(기본 2회, 1초 간격)하고 `status: RETRYING`으로 알림. 실행 타임아웃은 스케줄러가 안전망으로 정리

### 6. 위치 기반 매장 안내

- 거리 계산 방식을 Haversine SQL / `earthdistance` / PostGIS 세 후보로 비교해 **PostGIS KNN으로 확정**
  - 영업 중 매장 공간 인덱스, 매장 태그 배열과 위치를 함께 담은 인덱스(`(geog, tags)`)
  - 동적 조건(영업 중)은 인덱스를 만들 수 없어 가까운 후보부터 확인 → 전국 4만 곳 규모에서 엣지케이스 19가지 중 18가지가 300ms 이내
- 업무별 매장 필터(신규가입 / 번호이동 / 명의변경 / 유심재발급), 영업시간 기반 영업 상태
- 위치 권한 거부 시 **법정동코드 기반 지역 검색 API**로 대체 (구현 완료)
- 매장 가상 데이터 150건 생성
- 남은 것: 사용자용 최근접 매장 엔드포인트 노출, 채팅 응답에 매장 결과 연결, 지도 표시

### 7. 인증과 세션 승계

- 세션(쿠키) 기반 인증: SSE 스트리밍 호환을 위해 토큰 대신 채택
- 이메일 가입, 로그인, 카카오 로그인, **이메일 계정 ↔ 카카오 계정 양방향 연결**
- 비회원도 `guestId`로 상담 가능하고, 로그인하면 비회원 시절 **대화 이력과 남긴 평가가 함께** 계정으로 승계
  - 동시 요청 경합에서도 한 번만 승계되도록 원자적 갱신
- 요청 시점마다 회원 상태, 권한을 다시 확인해, 세션이 살아 있어도 정지, 탈퇴 계정은 차단

### 8. 답변 평가

- 완료된 답변(`ANSWER` / `STORE_RESULT`)만 평가 대상. 되묻기, 실패 메시지는 제외
- 👍는 사유 없이, 👎는 사유 필수(`WRONG_INFO` / `NOT_RELATED` / `HARD_TO_READ`) + 의견 1,000자
- 대화 이력 응답에 `ratable` / `myFeedback`을 함께 내려 새로고침 후에도 평가 상태가 유지됨

### 9. 관리자 기능

- FAQ 조회, 등록, 수정, 삭제 + **낙관적 락으로 동시 수정 방지**(다른 관리자가 먼저 수정하면 충돌로 거절)
- FAQ 버전, 내용 해시, 인용 횟수를 함께 보여줘 임베딩 동기화 필요 여부를 판단
- 매장 목록, 상세 조회(키워드, 상태 필터, 기본은 영업 중만)
- `/api/v1/admin/**`은 `ADMIN` 역할로 제한

</details>

```
├── chat        상담 세션 / 메시지 / 실행 단위 / SSE 구독 레지스트리

├── rag         Context 구성 / Answer Guard / 답변 근거 스냅샷
├── llm         Ollama 연동 / 재시도 / 생성 이력
├── feedback    답변 평가 수집
├── faq         FAQ 원본 / 이중 벡터 임베딩 / 검색
├── member      회원 / 비회원 / 소셜 계정 / 상태, 권한 필터
├── store       매장 / 영업시간 / 취급 업무 / PostGIS 최근접 검색
└── global      공통 응답 / 예외 / 설정
```

### 2차에서 바뀐 것: 상담 흐름의 주인을 하나로 정리

1차에서는 채팅 처리 구현이 여러 갈래로 나뉘어 있었습니다. 2차에서 **`consult`의 `ConsultChatProcessingService` 하나가 턴 전체를 책임지도록 통합**했습니다(TELME-90).

```
POST /chat/sessions/{id}/messages
   └ chat: 사용자 메시지, 실행 저장 → 처리 요청
        └ consult: ConsultChatProcessingService
             ├ intent  : 의도 분류, 복합 질문 분해, 후속 답변 해석
             ├ 되묻기   : 조건이 비면 CLARIFICATION 저장하고 턴 종료
             ├ faq     : 이중 벡터 검색 (원문 → 실패 시 정제 질문)
             ├ rag+llm : 근거 기반 답변 생성 → Answer Guard
             └ 저장 후  : chat의 SSE 레지스트리로 token / complete 전달
```

경계 두 개를 인터페이스로 끊어 뒀습니다.

- `ChatProcessingPort`: chat은 "처리해 달라"고만 요청하고, 누가 어떻게 처리하는지 모릅니다
- `ConsultChatEvents`: 상담 처리는 SSE를 직접 알지 못하고, **DB 저장이 끝난 뒤에만** 이벤트 전달을 호출합니다

두 번째가 2차에서 고친 버그의 핵심입니다. 전달이 실패해도 저장된 답변은 그대로 남아야 하고, 저장 전에 보낸 답변이 화면에만 있다가 새로고침하면 사라지는 일이 없어야 합니다(TELME-92 / 93).

</details>

<summary><b>설계에서 신경 쓴 3가지</b></summary>

1. **`message_sources`를 스냅샷으로 둔 것**: FAQ가 나중에 수정되거나 삭제돼도 과거 답변의 근거는 그대로 남아야 합니다. FK로 현재 값을 따라가면 "그때 뭘 근거로 답했는지"를 잃습니다. 그래서 제목, 버전, 수정일, 유사도를 답변 시점 값으로 복사해 보관합니다.

2. **`chat_executions`와 `consult_requests`의 생명주기를 분리한 것**: 실행(execution)은 사용자 메시지 한 번을 처리하는 수 초짜리 단위이고, 상담 요청(consult request)은 조건을 되묻느라 여러 턴에 걸쳐 살아 있습니다. 하나로 합치면 되묻기 상태를 추적할 수 없습니다.

3. **`faq_embeddings.faq_version`과 `sync_status`**: 원본과 임베딩이 어긋나는 상황을 감지하기 위한 장치입니다. `faqs.version`과 비교해 재임베딩이 필요한 행을 찾고, 부분 인덱스로 동기화가 안 끝난 행만 빠르게 조회합니다.

4. **(2차 추가) 벡터 컬럼을 두 개로 늘린 것**: `embedding`(`Q_A`)과 `embedding_question`(`QUESTION_ONLY`)을 같은 행에 두고 컬럼마다 HNSW 인덱스를 만듭니다. 테이블을 나누지 않은 이유는 두 벡터가 **같은 FAQ 버전에서 함께 만들어져야** 하기 때문입니다. 한 행이면 동기화 상태를 하나로 관리할 수 있습니다.

### 임베딩 모델 - 후보 3종 (기획 단계 측정, FAQ 1,000건, top-k=5)

| 모델 | 차원 | Recall@3 | 질의 임베딩 | 판단 |
| --- | --- | --- | --- | --- |
| **bge-m3** | 1024 | 92% | **42ms** | **채택** |
| multilingual-e5-large | 1024 | 93% | 157~262ms | Recall 1%p 높지만 2.1배 느림 |
| nomic-embed-text | 768 | 20% | 30ms | 탈락 |

`nomic`은 정확도 미달이 문제였지만, 더 큰 문제는 **틀린 결과에도 0.75~0.83의 높은 점수**를 줬다는 점입니다. 점수 자체에 변별력이 없으면 "유사도가 낮으면 답하지 않는다"는 우리 핵심 기능이 원리적으로 작동하지 않습니다.

### Vector DB - pgvector vs Qdrant

같은 벡터를 넣었더니 **검색 품질 지표가 소수점까지 동일**했습니다. 차이는 속도뿐이었습니다.

| 건수 | pgvector | Qdrant |
| --- | --- | --- |
| 1,000 | 6.0ms | 3.6ms |
| 10,000 | 8.9ms | 3.9ms |

둘 다 목표(500ms)의 2% 이내라 **성능은 선택 기준이 되지 못했습니다.** 자원도 Qdrant가 오히려 가벼웠습니다(151MB vs 187MB).

그래서 다른 기준으로 갈랐습니다. **FAQ 원본과 임베딩을 같은 트랜잭션으로 묶을 수 있는지**입니다. Qdrant를 쓰면 DB와 벡터 저장소에 나눠 쓰게 되고, 한쪽만 성공했을 때의 정합성을 애플리케이션이 직접 책임져야 합니다. 그 개발 비용 때문에 제외했습니다.

### LLM - 후보 4종

| 모델 | 첫 토큰 | 전체 | 판단 |
| --- | --- | --- | --- |
| **exaone3.5:7.8b** | 2.5s | 7.2s | **채택** |
| llama3.1:8b | 2.3s | 4.5s | 답변이 1문장으로 끝나거나 직전 답변 재사용 |
| gemma3:4b | 1.9s | 5.4s | 정확도는 무난하나 형식 문제 |
| qwen3:8b | **14.4s** | 17.5s | thinking 모드로 속도 미달 |

속도만 보면 `llama`가 가장 빨랐지만, **프롬프트를 3버전 바꿔가며 재평가한 결과 `exaone`만 일관되게 지시를 따랐습니다.**

`gemma3:4b`에서는 규칙을 조이면 "확인이 어렵습니다"를 남발하고, 풀면 없는 답을 지어냈습니다. 균형점이 없었습니다. **규칙을 늘릴수록 소형 모델은 규칙 텍스트의 단어를 출력에 그대로 반영**하는 경향을 확인했습니다.

### 유사도 임계값: 0.72로 확정 (실측 완료)

기획 단계 잠정값은 0.7이었습니다. 1차에서 30건 평가셋으로 0.71을 골랐고, 1,150건 적재 후 130건 평가셋으로 다시 격자 측정해 **0.72로 확정**했습니다.

격자 설계: 임베딩 구성 4 × top-k 4 × 임계값 31 = **496조합**. 단순 반복이면 22시간이지만, 검색 결과가 점수 내림차순이라는 성질을 이용해 임계값 0 / top-10 결과 한 번만 받아 오프라인에서 다시 걸러 **11분**에 끝냈습니다.

| 설정 | 확정값 | 근거 |
| --- | --- | --- |
| `faq.embedding-text.variant` | `Q_A` (질문 + 답변) | 구성 4종 비교 |
| `search.similarity-threshold` | **0.72** | 거부율 0.94 유지 구간의 Recall 최대 |
| top-k | 3 | top-3 이상은 값이 동일 |
| `search.dual-vector.question-threshold` | **0.88** | 무관 70건 중 62건 거부 + ANSWER 손실 0건 조건의 최대 Recall |

### 1,150건 실측: 그리고 "92%"가 왜 46%가 됐나

| 지표 | 단일 벡터 (1차) | **이중 벡터 (현행)** |
| --- | --- | --- |
| Recall@1 | 0.312 | **0.412** |
| Recall@3 | 0.375 | **0.463** |
| MRR | 0.338 | **0.435** |
| 무관 질문 거부율 (50건) | 0.940 | 0.940 |
| 무관 질문 거부율 (70건) | 0.886 | 0.886 |

기획 단계의 Recall@3 92%는 **FAQ 질문을 변형한 쉬운 질문 + 임계값 없이** 랭킹만 본 값이었습니다. 1,150건으로 늘리고, 실제 운영 임계값(0.72)을 적용하고, 표현이 다른 질문을 섞은 평가셋으로 바꾸자 **0.375까지 떨어졌습니다.** 지표가 나빠진 게 아니라, **그동안 측정이 쉬웠던 것**입니다.

떨어진 값을 보고 원인을 분류했습니다. 긍정 질문 80건을 "1등이 정답인가 × 1등 점수가 임계값을 넘는가"로 4분할했습니다.

| 그룹 | 1등이 정답 | 점수 ≥ 0.72 | 결과 | 건수 |
| --- | --- | --- | --- | --- |
| A | O | O | 정답이 1위로 전달 | 25 |
| B | O | X | **정답인데 컷에서 잘림** | 18 |
| C | X | X | 결과 없음 | 25 |
| D | X | O | 1위는 오답 (5건은 정답이 2–3위로 함께 전달) | 12 |

**문제는 랭킹이 아니라 컷이었습니다.** 정답이 이미 상위에 와 있는데 임계값에서 잘리는 게 18~25건. 임계값만 내리면 무관 질문 거부율이 같이 무너집니다. 그래서 2차에서는 임계값을 건드리지 않고 **신호를 하나 더 얹는** 이중 벡터를 택했습니다.

### 이중 벡터 vs 리랭커: 왜 이중 벡터를 먼저 넣었나

답변 가능 110 / 무관 70, 같은 라벨, 같은 임계값 선택 규칙으로 비교했습니다.

| 구성 | 임계값 | 공식 라벨 | 다중 정답 라벨 | 무관 통과 | 지연 평균 / p95 |
| --- | --- | ---: | ---: | ---: | --- |
| 단일 벡터 (1차) | `Q_A` 0.72 | 52 | 59 | 8 | 기준 |
| **이중 벡터 (채택)** | `QUESTION_ONLY` 0.88 | **59** (+7) | **64** (+5) | 8 | **×1.09 / ×1.15** |
| 리랭커 | 0.82 | 61 (+9) | 70 (+11) | 7 | ×6.9 / ×6.5 |
| 리랭커 + 이중 벡터 (오프라인) | 0.82 + 0.90 | 64 (+12) | 72 (+13) | 7 | 미측정 |

리랭커가 효과는 더 크지만 **검색 지연이 7배**(중앙값 62ms → 422ms, p95 84ms → 549ms)입니다. 이중 벡터는 임베딩 호출을 늘리지 않고 DB 조회만 2회라 지연이 9%만 늘었습니다. 효과당 비용이 더 나은 쪽을 먼저 넣고, 리랭커는 조건부 후보로 남겼습니다.

### 답변 품질: 환각률 20.2% → 10.8%

검색이 아니라 **답변 생성 단계**를 따로 측정했습니다. 답변을 문장 단위로 `supported` / `unsupported`(환각) / `irrelevant`로 판정하고, `환각률 = unsupported / 전체 문장`으로 봅니다.

- 130건 평가셋의 긍정 질문은 FAQ 질문을 변형한 것이라 모델이 지어낼 이유가 없었습니다(환각 2.3%). **근거를 그대로 옮겨 쓸 수 없는 질문 20건을 따로 만들어** 환각을 유도했습니다.
- 측정 중에는 `temperature=0`으로 고정하고, 두 번 돌려 글자까지 같은지 확인했습니다. 측정 호출은 `llm_generations`에 기록하지 않아 운영 통계를 오염시키지 않습니다.
- 프롬프트와 Answer Guard를 단계별로 바꿔 **기준선 20.2% → 10.8%**로 줄였습니다.

> 주의해서 읽어야 하는 수치입니다. 10.8%는 **답변이 생성된 60건 안에서의 비율**이고, 150건 전체로 보면 답변 자체가 나오지 않은 경우가 더 많습니다. 환각률만 보면 "과도한 보류"가 보이지 않습니다 - 이게 2차 멘토링 질문 A-3의 배경입니다.

### 임계값 0.6 검토: 아직 반영하지 않은 이유

임계값을 0.6으로 낮추고 근거 적합성 판정기를 붙이면 어떻게 되는지 측정했습니다(130건 / 1,150건 기준).

| 구성 | 같은 정책 근거 전달 (80) | 근거 없음 (80) | 답 없는 질문 통과 (50) |
| --- | ---: | ---: | ---: |
| 현행 develop, 0.72 | 37 | 43 | 3 |
| 0.72 + EXAONE 판정 | 33 | 47 | 1 |
| **0.6 + EXAONE 판정** | **69** | **10** | 7 |
| 리랭커 + EXAONE 판정 | 72 | 6 | 7 |

근거 전달은 33 → 69로 크게 늘지만 답 없는 질문 통과도 1 → 7로 늘어납니다. **이득과 위험이 함께 커지는 변경**이라 운영값은 0.72로 두고, 검토 문서로만 남겼습니다(`docs/SEARCH_THRESHOLD_060_AND_ANSWER_QUALITY.md`).

### 평가셋을 늘려온 과정

| 평가셋 | 건수 | 용도 |
| --- | --- | --- |
| `eval_questions_30` | 30 | 1차 임계값 결정 |
| `eval_questions_130` | 130 (긍정 80 + 무관 50) | 주 측정셋 |
| `eval_questions_180_multigold` | 180 | 다중 정답 라벨: 정답이 여러 FAQ일 때 하나만 정답으로 보던 과소평가 보정 |
| `eval_questions_holdout_90` | 90 | 임계값 선택에 쓰지 않은 검증용 |
| `eval_questions_supplement_50` | 50 | 보강 |
| `eval_answer_quality_20` | 20 | 환각 유도 |
| `eval_selfretrieval_1150` | 1,150 | FAQ 자기 검색(적재, 임베딩 정합성) |

유사 후보 598쌍 중 LLM이 두 차례 모두 동등하다고 판정한 246쌍을 다중 정답으로 추가했습니다. 경계 점수 구간(0.87~0.92) 문항을 늘리려고 탐색 문항 16건을 따로 만들었지만 목표 구간은 0/16이었고, **점수에 맞춰 문항을 고치지 않고 결과를 그대로 보존**했습니다.

### 환경별 편차 - 같은 실험, 다른 결과

6명이 각자 환경에서 재현했더니 하드웨어에 따라 결과가 크게 달랐습니다.

| 지표 | Ryzen 7 / Windows | M5 Pro / macOS Docker |
| --- | --- | --- |
| 질의 임베딩 (bge-m3) | 46ms | **170ms** (3.7배 느림) |
| LLM 전체 | 11.2s | **7.2s** (빠름) |

macOS Docker는 GPU(Metal)를 컨테이너에 전달하지 못해 임베딩이 느리고, 대신 통합 메모리 대역폭이 높아 LLM 생성은 빨랐습니다.

같은 모델을 두고도 "7.8b는 쓸 수 없다"(16GB 환경)와 "7.8b가 최선이다"(48GB 환경)로 결론이 갈렸습니다. **배포 대상 EC2 인스턴스에서 재측정이 필요하다**는 것이 공통 결론입니다.

## 멘토링 질문 리스트 (2차)

<details>
<summary><b>A. 환각 차단과 답변 보존</b></summary>

1. 규칙 기반 Guard와 모델 기반 검증의 범위 (서희)
   근거 밖 기간, 비용, 조건을 생성하지 않도록 Answer Guard를 두었습니다. 여기에 "이 근거로 답할 수 있나"를 LLM이 한 번 더 확인하는 단계를 붙이려 합니다.

- 규칙 기반으로 확실하게 처리할 범위와 모델 기반 검증이 필요한 범위를 어떻게 나누시나요?
- 검색 조건을 느슨하게 하면 근거가 약한 문서도 넘어갑니다. 검증 단계를 먼저 넣고 완화하는 순서가 맞을까요?

2. 부분 근거만 있을 때의 처리 (지민, 서희)
   FAQ가 "로밍 신청은 1시간 이내 적용"을 안내할 때 사용자가 "로밍 해지는 언제 적용되나요"를 물으면, 저희는 거부로 처리했습니다.

- 거부 / 부분 답변("해지는 안내가 어렵고, 신청은 1시간 이내입니다") / 상담원 연결 중 실무는 어느 쪽인가요?
- 한 답변에 근거 있는 내용과 없는 내용이 섞이면 일부 제거, 수정, 재생성, 전체 보류 중 무엇을 기준으로 선택하시나요?

3. 과도한 보류를 지표로 추적하시나요? (지민)
   환각을 줄이려고 조건을 엄격하게 하면, 답할 수 있는 질문에도 "정보가 없다"고 답하는 경우가 생깁니다. 환각률만 보면 이 손실이 보이지 않았습니다.

- 과도한 보류를 별도 지표로 추적하시나요? 환각률과 어떻게 함께 보시나요?

</details>

<details>
<summary><b>B. 평가셋과 지표 신뢰도</b></summary>

1. 임계값 확정 방법 (지민)
   검색 유사도 임계값을 평가셋으로 골랐는데, 어느 쪽이 나은지 가려줄 평가 문항이 거의 없었습니다.

- 실무에서는 임계값을 어떻게 확정하시나요? 사용자 로그, A/B 테스트, 보수적인 값 고정 후 다른 장치로 보완 중 어느 쪽인가요?

2. LLM Judge 결과의 신뢰도 (지민, 서희, 용재)
   LLM에게 답변을 문장별로 "근거에 있나"를 채점하게 했습니다. 사람이 다시 보니 일부는 오판이었고, 같은 답변을 재채점하면 판정이 바뀌기도 했습니다.

- Judge 결과를 그대로 지표로 쓰시나요, 사람 검토를 섞으시나요?
- 평가 대상이 답변 불가, 차단으로 달라지면 분모가 바뀌어 비율이 흔들립니다. 질문별 정확도, 거절 적절성과 문장별 근거성을 어떻게 함께 보고하시나요?

3. 평가셋 규모와 사용자 로그 전환 시점 (지민)
   평가 질문이 130건이라 지표가 1~2건 차이로 갈립니다.

- 실무에서 보는 최소 규모는 어느 정도인가요?
- 오프라인 평가셋 대신 사용자 로그를 쓰기 시작하는 시점이 궁금합니다.

4. 평가셋 과적합과 분리 (지민, 신형)
   임계값을 고를 때 쓴 평가셋으로 다시 검증하면 순환 논증이 됩니다. 처음 보는 질문 세트를 따로 만들었는데, 한 번 쓰면 소진되어 매번 만들기가 부담입니다.

- 선택용과 검증용 평가셋을 나누시나요? 아니면 사용자 로그를 기간으로 나눠 쓰시나요?
- 평가셋을 얼마나 자주 교체하거나 추가하시나요?

5. 사람이 전수 검토를 못 할 때의 표본 기준 (용재, 서희)
   복수 정답 라벨링에서는 유사 후보 598쌍 중 LLM이 두 차례 모두 동등하다고 판정한 246쌍을 추가했고, 답변 품질 검토에서는 critical 사례와 판정 불일치 사례를 먼저 보고 나머지는 표본으로 확인했습니다.

- 전체를 다 볼 수 없을 때 표본 비율을 몇 % 정도로, 어떤 기준으로 뽑으시나요?

   RAG를 써도 LLM이 컨텍스트 밖의 내용을 지어내는 경우가 있었습니다. 저희 테스트에서도 참고자료에 없는 타사 브랜드를 언급한 사례가 나왔습니다. 현업에서는 이걸 어떻게 측정하고 관리하시나요?

3. 되묻기 기능의 품질 평가
   조건 되묻기가 상담 품질을 개선했는지 평가하려고 합니다. 현업에서 중요하게 보는 기준이나 테스트 사례가 궁금합니다.
