> LG유플러스 유레카 백엔드 과정 / 최종 융합 프로젝트 / 팀 무도(무엇을 도와드릴까요?)

## 프로젝트 개요

가상 통신사의 FAQ 1,000건을 근거로 사용자 질문에 답하고, 가까운 매장까지 안내합니다.

```
"유심 재발급 얼마예요?"
      ↓
  FAQ 검색 → 근거 있음 → AI가 근거로 답변 + 출처 표시
      ↓
  FAQ 검색 → 근거 없음 → "확인이 어렵습니다" (AI를 아예 호출하지 않음)
```

**프로젝트 목적**
- FAQ를 근거로 한 신뢰성 있는 AI 상담 구현
- 위치 기반 매장 안내를 상담 흐름에 통합
- 검색 품질을 정량 지표로 관리하는 개선 체계 수립

| |                                 |
| --- |---------------------------------|
| **기간** | 2026-09-16 ~ 10-25 (6주, MVP 3단계) |
| **팀** | 8명 (백엔드/인프라 중심, 프론트 바이브코딩)      |
| **현재** | 1차 MVP 진행 중         |

## 주요 기능

| | 기능 | 한 줄 설명 |
| --- | --- | --- |
| 1 | **FAQ 데이터 구축** | 정책 문서를 먼저 만들고 그 수치만 인용하게 제약해 1,000건 생성 |
| 2 | **벡터 검색** | 질문을 벡터로 바꿔 의미가 비슷한 FAQ를 찾음 |
| 3 | **AI 상담** | 찾은 FAQ를 근거로 답변 생성. 근거 없으면 답하지 않음 |
| 4 | **실시간 응답** | 답변이 타이핑되듯 한 글자씩 도착 (SSE) |
| 5 | **매장 안내** | 현재 위치에서 가까운 매장을 지도에 표시 |
| 6 | **비회원 상담** | 로그인 없이 상담하고, 나중에 가입하면 대화 이력을 이어받음 |

<details>
<summary><b>기능별 상세 보기</b></summary>

### 1. FAQ 데이터 구축과 품질 관리

- 정책 기준 문서(`docs/POLICY.md`) 45개 항목을 먼저 확정하고, FAQ 답변은 그 수치만 인용
- 카테고리 10종 × 질문유형 5종 × 페르소나 3종 조합으로 표현 다양성 확보
- 임베딩 유사도 0.95 이상 중복 자동 탐지, 답변 수치와 정책 문서 값 자동 대조

### 2. 벡터 검색 (RAG Retrieval)

- `bge-m3` 임베딩(1024차원) → pgvector 코사인 거리 top-k 검색
- 검색 품질을 Recall@k, MRR로 측정하고 개선 전후를 비교

### 3. AI 상담 파이프라인

- 질문 의도 분류(`FAQ` / `STORE` / `BOTH` / `UNKNOWN`)와 복합 질문 분해
- 검색 결과로 Context를 구성하고 EXAONE 3.5로 근거 기반 답변 생성
- 상담에 필요한 조건이 빠졌으면 되묻고, 후속 답변과 조건 정정을 반영

### 4. 실시간 응답

- SSE 토큰 스트리밍, `GENERATING` / `COMPLETE` / `FAILED` / `RETRYING` 4종 상태 전이
- `Last-Event-ID` 기반 유실 이벤트 재전송, 생성 중단 처리
- Resilience4j로 타임아웃 감지와 자동 재시도

### 5. 위치 기반 매장 안내

- 현재 위치 기준 최근접 매장 계산, 채팅 응답과 지도 동시 표시
- 업무별 매장 필터(신규가입 / 번호이동 / 명의변경 / 유심재발급), 영업 상태 기반 안내
- 위치 권한 거부 시 지역 검색, 지도 API 실패 시 텍스트 주소로 대체

### 6. 인증과 세션 승계

- 세션(쿠키) 기반 인증 — SSE 스트리밍 호환을 위해 토큰 대신 채택
- 비회원도 `guestId`로 상담 가능하고, 로그인하면 비회원 시절 대화 이력과 자동 연결

</details>

<details>
<summary><b>설계에서 신경 쓴 3가지</b></summary>

1. **`message_sources`를 스냅샷으로 둔 것**: FAQ가 나중에 수정되거나 삭제돼도 과거 답변의 근거는 그대로 남아야 합니다. FK로 현재 값을 따라가면 "그때 뭘 근거로 답했는지"를 잃습니다. 그래서 제목·버전·수정일·유사도를 답변 시점 값으로 복사해 보관합니다.

2. **`chat_executions`와 `consult_requests`의 생명주기를 분리한 것**: 실행(execution)은 사용자 메시지 한 번을 처리하는 수 초짜리 단위이고, 상담 요청(consult request)은 조건을 되묻느라 여러 턴에 걸쳐 살아 있습니다. 하나로 합치면 되묻기 상태를 추적할 수 없습니다.

3. **`faq_embeddings.faq_version`과 `sync_status`**: 원본과 임베딩이 어긋나는 상황을 감지하기 위한 장치입니다. `faqs.version`과 비교해 재임베딩이 필요한 행을 찾고, 부분 인덱스로 동기화가 안 끝난 행만 빠르게 조회합니다.

</details>

## 기술 스택

기획 단계에서 팀원 6명이 각자 환경에서 **같은 실험을 재현해** 후보를 비교하고 결정했습니다.

| 영역 | 선택 | 왜 이걸 골랐나 |
| --- | --- | --- |
| **임베딩** | bge-m3 (1024차원) | 후보 3종 비교. Recall@3 92%, 질의 임베딩 42ms |
| **Vector DB** | PostgreSQL + pgvector | Qdrant와 검색 품질 동일. FAQ 원본과 벡터를 **한 트랜잭션**으로 묶을 수 있어 선택 |
| **LLM** | EXAONE 3.5 7.8B | 후보 4종 비교. 프롬프트 지시를 일관되게 따른 유일한 모델 |
| **응답 방식** | SSE 스트리밍 | 전체 응답이 약 10초라 단건 응답은 사용성 미달 |
| **검색 방식** | 벡터 단독 | Recall@3 92%로 현재 충분. 하이브리드·리랭커는 조건부 후보로 보류 |
| Backend | Java 21 / Spring Boot 3.5.16 | |
| 인증 | Spring Security (세션 기반) | SSE 스트리밍 호환을 위해 토큰 대신 세션 |
| 스키마 관리 | Flyway | `ddl-auto` 미사용. 스키마를 코드로 관리 |
| Frontend | React / Vite / TypeScript / Tailwind | |
| 지도 | 카카오맵 JavaScript SDK | |
| Infra | Docker Compose / AWS / Terraform / GitHub Actions | |
| 협업 | GitHub / Jira / Notion / Slack | |

<details>
<summary><b>실험 결과 자세히 보기</b></summary>

### 임베딩 모델 - 후보 3종 (FAQ 1,000건, top-k=5)

| 모델 | 차원 | Recall@3 | 질의 임베딩 | 판단 |
| --- | --- | --- | --- | --- |
| **bge-m3** | 1024 | 92% | **42ms** | **채택** |
| multilingual-e5-large | 1024 | 93% | 157~262ms | Recall 1%p 높지만 2.1배 느림 |
| nomic-embed-text | 768 | 20% | 30ms | 탈락 |

`nomic`은 정확도 미달이 문제였지만, 더 큰 문제는 **틀린 결과에도 0.75~0.83의 높은 점수**를 줬다는 점입니다. 점수 자체에 변별력이 없으면 "유사도가 낮으면 답하지 않는다"는 우리 핵심 기능이 원리적으로 작동하지 않습니다.

### Vector DB - pgvector vs Qdrant

같은 벡터를 넣었더니 **검색 품질 지표가 소수점까지 동일**했습니다. 차이는 속도뿐이었습니다.

| 건수 | pgvector | Qdrant |
| --- | --- | --- |
| 1,000 | 6.0ms | 3.6ms |
| 10,000 | 8.9ms | 3.9ms |

둘 다 목표(500ms)의 2% 이내라 **성능은 선택 기준이 되지 못했습니다.** 자원도 Qdrant가 오히려 가벼웠습니다(151MB vs 187MB).

그래서 다른 기준으로 갈랐습니다. **FAQ 원본과 임베딩을 같은 트랜잭션으로 묶을 수 있는지**입니다. Qdrant를 쓰면 DB와 벡터 저장소에 나눠 쓰게 되고, 한쪽만 성공했을 때의 정합성을 애플리케이션이 직접 책임져야 합니다. 그 개발 비용 때문에 제외했습니다.

### LLM - 후보 4종

| 모델 | 첫 토큰 | 전체 | 판단 |
| --- | --- | --- | --- |
| **exaone3.5:7.8b** | 2.5s | 7.2s | **채택** |
| llama3.1:8b | 2.3s | 4.5s | 답변이 1문장으로 끝나거나 직전 답변 재사용 |
| gemma3:4b | 1.9s | 5.4s | 정확도는 무난하나 형식 문제 |
| qwen3:8b | **14.4s** | 17.5s | thinking 모드로 속도 미달 |

속도만 보면 `llama`가 가장 빨랐지만, **프롬프트를 3버전 바꿔가며 재평가한 결과 `exaone`만 일관되게 지시를 따랐습니다.**

`gemma3:4b`에서는 규칙을 조이면 "확인이 어렵습니다"를 남발하고, 풀면 없는 답을 지어냈습니다. 균형점이 없었습니다. **규칙을 늘릴수록 소형 모델은 규칙 텍스트의 단어를 출력에 그대로 반영**하는 경향을 확인했습니다.

### 유사도 임계값 - 현재 0.45 (잠정)

답이 있는 질문과 없는 질문의 점수 분포가 **크게 겹칩니다.**

| 구분 | 최소 | 중앙값 | 최대 |
| --- | --- | --- | --- |
| 답 있는 질문 | 0.499 | 0.624 | 0.739 |
| 답 없는 질문 | 0.313 | 0.528 | **0.703** |

답 없는 질문의 최대(0.703)가 답 있는 질문의 최소(0.499)보다 높습니다. **단일 임계값으로는 두 그룹을 깨끗이 가를 수 없다**는 뜻입니다.

임계값을 0.65로 올리면 오답은 93% 걸러지지만 **정답의 30%도 함께 거절**됩니다. 상담 서비스에서 정답 1/3을 "확인이 어렵습니다"로 돌리는 건 받아들이기 어렵습니다.

→ **임계값 단독으로는 이 기능을 완성할 수 없다**는 결론입니다. 프롬프트의 근거 제한 규칙과 의도 분류를 함께 써야 합니다. 1차 MVP의 주요 과제입니다.

### 환경별 편차 - 같은 실험, 다른 결과

6명이 각자 환경에서 재현했더니 하드웨어에 따라 결과가 크게 달랐습니다.

| 지표 | Ryzen 7 / Windows | M5 Pro / macOS Docker |
| --- | --- | --- |
| 질의 임베딩 (bge-m3) | 46ms | **170ms** (3.7배 느림) |
| LLM 전체 | 11.2s | **7.2s** (빠름) |

macOS Docker는 GPU(Metal)를 컨테이너에 전달하지 못해 임베딩이 느리고, 대신 통합 메모리 대역폭이 높아 LLM 생성은 빨랐습니다.

같은 모델을 두고도 "7.8b는 쓸 수 없다"(16GB 환경)와 "7.8b가 최선이다"(48GB 환경)로 결론이 갈렸습니다. **배포 대상 EC2 인스턴스에서 재측정이 필요하다**는 것이 공통 결론입니다.

## 팀 구성과 역할 분담

**조장** 구지민 / **조원** 박서희, 박신형, 박찬영, 변우림, 이용재, 최정현, 함세연

1차 MVP는 **AI 파트 6명**이 상담 파이프라인 전 구간을, **데이터 파트 2명**이 FAQ 데이터와 검색 기반을 맡습니다.

<details>
<summary><b>담당별 역할</b></summary>

### AI 파트

| 담당 | 역할 |
| --- | --- |
| 변우림 | 질문 의도 분류, 복합 질문 분해, 라우팅 |
| 함세연 | RAG Context 구성, Ollama + EXAONE 답변 생성 |
| 이용재 | 대화 세션 단위 저장, 채팅 이어하기 |
| 최정현 | SSE 기반 LLM 응답 실시간 스트리밍 |
| 박서희 | 상담 조건 확인·되묻기, 답변 품질 평가 |
| 박찬영 | 상담 피드백 저장·조회 API |

### 데이터 파트

검색 품질을 양쪽에서 다루기 위해 **읽기 경로와 쓰기 경로로 나눴습니다.**

```
박신형 (A)   읽기 경로   질문 → 임베딩 → 검색 → 측정
구지민 (B)   쓰기 경로   FAQ  → 임베딩 → 적재 → 동기화
```

둘 다 임베딩 호출·pgvector·튜닝·정량 측정을 경험하되 대상과 방향이 다릅니다. A는 임계값과 top-k를, B는 임베딩 텍스트 구성과 청킹 도입 여부를 다룹니다.

**튜닝 실험은 한 번에 하나씩만 바꾸고, 측정 스크립트는 하나만 씁니다.** 여러 명이 동시에 튜닝하면 수치가 왜 변했는지 추적할 수 없기 때문입니다.

> 2차 MVP부터는 전원 역할을 재분담합니다.

</details>

<details>
<summary><b>단계별 상세 항목</b></summary>

### 1차 MVP — AI 상담 파이프라인 완성 + 데이터 기반 구축

- FAQ 1,000건 생성, 임베딩 적재, 검색 정확도 측정
- 회원가입·로그인, 비회원 세션, Docker Compose, CI 파이프라인

### 작업 흐름

```
Jira 이슈 생성 → 브랜치 생성 → 구현 → PR → CI 통과 → 리뷰 → 머지

브랜치  <type>/<이슈키>-<요약>     feat/TELME-19-search-embedding-interface
커밋    <이슈키> <type>: <설명>    TELME-19 feat: 검색 인터페이스 정의
PR      [Type] 내용 (이슈키)       [Feat] 검색 인터페이스 정의 (TELME-19)
```

`main`과 `develop`에는 직접 커밋하지 않고, 리뷰어 승인 후 리뷰어가 Squash merge 합니다.

### CI에서 막는 것

로컬에서만 도는 검사는 결국 지켜지지 않아서, 자동화할 수 있는 것은 CI로 옮겼습니다.

| 검사 | 왜 필요한가 |
| --- | --- |
| 빌드 · 테스트 | |
| **이미 머지된 마이그레이션 수정 차단** | CI는 매번 빈 DB라 이 문제를 구조적으로 못 잡습니다. 팀원 로컬과 운영 DB만 깨집니다 |
| **엔티티 ↔ 스키마 일치 검증** | `ddl-auto=validate`로 컨텍스트를 올려 확인합니다 |
| **운영 프로파일에 로컬 시드 미포함 검증** | 설정 한 줄이 사라지면 운영 DB에 더미 계정이 들어갑니다 |
| 테스트 결과 PR 리포트 | 실패한 테스트를 PR에서 바로 확인 |

## 멘토링 질문 리스트

<details open>
<summary><b>A. 운영 판단 기준</b></summary>

**A-1. 답할 수 없다고 판단하는 기준**

저희는 검색 유사도가 낮으면 "확인이 어렵다"고 답하도록 임계값을 두려고 합니다. 그런데 측정해보니 답이 있는 질문과 없는 질문의 점수 분포가 크게 겹쳐서, 단일 임계값으로는 깨끗이 가를 수 없었습니다.

- 실무에서는 이 기준을 어떻게 정하시나요?
- 임계값 미만이어도 1등 결과를 답변하는 편인지, 정해진 안내만 하고 상담원 연결로 넘기는지 궁금합니다
- **잘못 답하는 것과 답을 안 하는 것 중 어느 쪽을 더 경계하시나요?**

**A-2. 상담원 연결 전환 기준**

AI 상담에서 상담원 연결로 전환하는 기준이 있나요? 검색 실패, 특정 업무 유형, 반복 질문 등 어떤 신호를 보시는지 궁금합니다.

**A-3. AI가 답하지 않도록 제한하는 영역**

요금 계산이나 해지 절차처럼 정확성이 중요한 업무는 AI가 답하지 않도록 제한하시나요? 그렇다면 그 경계를 어떻게 정하시는지 궁금합니다.

</details>

<details>
<summary><b>B. 품질 측정</b></summary>

**B-1. 검색 품질을 어떻게 관리하시나요**

저희는 평가 질문 30건으로 Recall@3를 측정하고, 임베딩 모델과 top-k를 바꿔가며 비교하고 있습니다.

- 실무에서는 검색 품질을 어떤 방식으로 관리하시나요?
- *(답변 후)* Recall 외에 NDCG나 Precision을 더 중요하게 보시나요? 오프라인 평가셋과 실제 사용자 로그 중 어느 쪽을 더 신뢰하시는지도 궁금합니다

**B-2. 할루시네이션 측정**

RAG를 써도 LLM이 컨텍스트 밖의 내용을 지어내는 경우가 있었습니다. 저희 테스트에서도 참고자료에 없는 타사 브랜드를 언급한 사례가 나왔습니다. 현업에서는 이걸 어떻게 측정하고 관리하시나요?

**B-3. 되묻기 기능의 품질 평가**

조건 되묻기가 상담 품질을 개선했는지 평가하려고 합니다. 현업에서 중요하게 보는 기준이나 테스트 사례가 궁금합니다.

</details>

<details>
<summary><b>C. 설계 판단</b></summary>

**C-1. 조건 되묻기를 어떻게 설계하시나요**

상담에 필요한 정보가 빠졌을 때 되묻는 기능을 만들고 있는데, **어느 시점에 무엇을 되물어야 하는지 판단이 어렵습니다.**

- 실무에서는 이 문제를 어떻게 접근하시나요?
- *(답변 후)* 질문만 보고 부족한 조건을 먼저 확인하는 방식과, FAQ를 1차 검색한 뒤 결과의 조건 분기를 기준으로 되묻는 방식 중 어느 쪽이 적절할까요? 필요한 정보를 상담 유형별 규칙으로 정의하는 것과 LLM이 맥락을 보고 판단하는 것은 어떻게 나누시나요?

**C-2. 멀티턴 맥락 관리**

멀티턴 대화에서 이전 맥락을 어떻게 관리하시나요? 적정선을 잡는 기준이 궁금합니다.

**C-3. 비회원 → 회원 데이터 이관**

비회원 세션을 회원가입 시 계정으로 이관하는 기능을 설계했습니다.

- 실무에서 게스트에서 회원으로의 데이터 이관을 안전하게 처리하는 방식이 궁금합니다
- 많은 서비스가 비회원 대화를 이어주지 않던데, 기술적 이유인지 정책적 판단인지도 궁금합니다

</details>

<details>
<summary><b>D. 실무 트렌드</b></summary>

**D-1. 벡터 DB 선택**

저희는 PostgreSQL + pgvector를 골랐습니다. Qdrant와 검색 품질이 동일했고, FAQ 원본과 벡터를 한 트랜잭션으로 묶을 수 있어서였습니다.

- 실무에서는 어느 규모까지 확장으로 버티시고, 전용 벡터 DB로 넘어가는 판단 기준이 있으신지 궁금합니다

**D-2. 하이브리드 검색** *(D-1 답변 후)*

하이브리드 검색도 처음부터 적용하시는지, 아니면 순수 벡터 검색의 한계가 확인된 뒤에 도입하시는지 궁금합니다. 저희는 벡터 단독으로 Recall@3 92%가 나와서 일단 보류했습니다.

**D-3. 프레임워크 도입 시점**

저희는 LangChain이나 LlamaIndex 없이 직접 구현했습니다. 실무에서 이런 프레임워크를 도입하는 판단 기준이 있으신지 궁금합니다.

**D-4. 실제 문의 유형 분포** *(모르실 수 있는 질문입니다)*

혹시 통신사 고객센터에 실제로 들어오는 문의는 어떤 유형이 많은지 아시나요? 저희가 FAQ를 카테고리별로 나눠 만들고 있는데, 실제 분포와 크게 다르면 조정하려고 합니다.

</details>

<details>
<summary><b>E. 커리어 (시간이 남으면)</b></summary>

**E-1. AI 시대의 백엔드 개발자**

AI 서비스가 늘어나는 상황에서 백엔드 개발자가 커리어를 어떻게 쌓아가야 할지 궁금합니다.

- *(답변 후)* AI 서비스에서 백엔드가 맡는 범위는 어디까지인가요? 모델 쪽은 별도 조직이 하고 백엔드는 연동만 하는지, 검색 품질까지 함께 보시는지 궁금합니다

**E-2. RAG 외의 기술**

RAG 외에 현업에서 많이 쓰이는 AI 기술이 있다면 키워드만이라도 알려주시면 감사하겠습니다.

</details>
